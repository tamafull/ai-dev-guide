ツールを使って資料を探し、答えまで組み立てるAgentを作る

Agentは「LLMを何度も呼ぶもの」ではなく、モデルが状況に応じてToolを選び、結果を観察し、必要なら次のToolへ進む実行系です。このハンズオンでは、ローカルのメモ群を必要な時だけ読み、会議ブリーフを作るAgentを実装します。

完成するもの

agent-demo/
├─ notes/
│  ├─ customer.md
│  ├─ roadmap.md
│  └─ incidents.md
└─ app.py

ユーザーが「Acmeとの会議準備をして」と頼むと、Agentがまず利用可能なメモを確認し、必要なファイルだけ読み、目的・論点・リスク・確認事項をまとめます。

1. 環境

python -m venv .venv
.venv\Scripts\activate
pip install openai-agents
set OPENAI_API_KEY=...

OpenAI Agents SDKは、Agent、Tool、handoff、guardrail、session、tracingなどの実行基盤を提供します。

2. 資料を作る

notes/customer.md:

# Acme
- 契約更新: 11月末
- 最重要要望: CSV export高速化
- 前回会議: 現状8分、目標2分以内

notes/roadmap.md:

# Roadmap
- CSV export改善: 11月第2週にstaging予定
- API v2: 12月preview

notes/incidents.md:

# Incidents
- 10/18: export worker遅延。原因はqueue backlog。
- 恒久対策はworker scalingとquery見直し。

3. Toolを作る

app.py:

from pathlib import Path
from agents import Agent, Runner
from agents.decorators import tool

NOTES = Path("notes")


@tool
def list_notes() -> list[str]:
    """List available note filenames."""
    return [p.name for p in NOTES.glob("*.md")]


@tool
def read_note(filename: str) -> str:
    """Read one note file. filename must be a basename returned by list_notes."""
    path = NOTES / filename
    if path.parent != NOTES or not path.exists() or path.suffix != ".md":
        return "ERROR: invalid filename"
    return path.read_text(encoding="utf-8")

Toolはなるべく小さく、入力・出力を明確にします。「任意shellを実行」のような巨大Toolより、用途が分かるToolの方が権限も絞れます。

4. Agentを定義する

agent = Agent(
    name="Meeting Prep",
    instructions="""
あなたは会議準備担当です。
必要な資料だけToolで確認し、推測で不足を埋めないでください。
出力は次の順:
1. 会議の目的
2. 現状
3. 論点
4. リスク
5. 相手へ確認する質問
最後に参照したファイル名を書く。
""",
    tools=[list_notes, read_note],
)


if __name__ == "__main__":
    result = Runner.run_sync(
        agent,
        "Acmeとの契約更新前の会議準備をして。CSV exportの状況も確認したい。",
    )
    print(result.final_output)

python app.py

Agentは必要に応じて list_notes、read_note を呼びます。普通の1回のLLM呼び出しとの違いは、資料内容をpromptへ最初から全部詰めず、モデルが作業途中に外部能力を使えることです。

5. Toolを使ったか確認する

Agentは結果が自然でも、必要な資料を実際に読んだとは限りません。SDKのtraceを確認し、Tool callと引数、結果、handoffなど実行履歴を見ます。

評価では最終文章だけでなく、次も確認します。

  • customer.mdを読んだか。
  • roadmap.mdまたはincidents.mdを必要に応じて読んだか。
  • 存在しない資料を参照していないか。
  • 不要な全ファイル読み込みをしていないか。

6. 「Agentにする意味」があるか確認する

もし毎回必ず3ファイルを読むだけなら、Pythonコードで3ファイルを読み、1回LLMへ渡す方が単純です。Agent化が有効なのは、入力ごとに次の行動が変わる場合です。

処理普通のコードAgent
決まった3ファイルを読む向く不要
質問に応じて資料を選ぶルールが複雑なら難しい向く
外部結果を見て次の検索を変える状態機械で実装可能探索が曖昧なら向く
送金・削除決定論＋承認が基本判断補助だけに留める

7. 書き込みToolを足すなら承認境界を作る

read_note は読み取りですが、メール送信やファイル削除は副作用があります。AgentへToolを渡す時は「使えるか」ではなく「どこまで自動実行してよいか」を分けます。

Agents SDKにはTool guardrailやhuman-in-the-loopの仕組みがあります。機密操作は、Tool呼び出し前に入力検証し、必要なら実行を一時停止して人の承認を待つ構成にします。

8. 状態を持たせる

会話を複数turn続ける場合、result.to_input_list() を次のRunnerへ渡す方法、sessionを使う方法、server-managed stateを使う方法があります。何でも会話履歴へ残すのではなく、長期状態は構造化ファイルやDBへ分離すると扱いやすくなります。

9. Agentの失敗パターン

症状対策
Toolを使わず推測する資料依存の質問をevalへ入れ、Tool usageを検証する。
全Toolを毎回呼ぶTool説明を具体化し、必要ならTool search /遅延ロード。
同じToolをループmax turns、同一失敗検出、stop criteria。
危険操作を勝手に実行読み書き分離、approval、guardrail、sandbox。
最後の文章は正しいが外部状態が違うTool結果・DB状態まで評価する。

10. 次に改造する

  • 検索Toolを追加して、ファイル数を100件へ増やす。
  • 会議ブリーフをファイル保存するToolを追加し、保存前だけ承認させる。
  • 同じ5タスクで「全資料をpromptへ入れる方式」とAgent方式を比較する。
  • traceからTool回数、latency、token使用量を記録する。
  • 次のMulti-Agent記事で、調査役を別Agentへ分離する。
