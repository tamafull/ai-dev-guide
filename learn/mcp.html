MCPサーバーを作り、ToolとResourceを実際に呼び出す

MCPはAIと外部能力をつなぐ共通プロトコルです。このページでは現在のPython SDK v2を使い、計算Toolと設定Resourceを公開し、MCP InspectorとPython Clientの両方から呼び出します。

完成するもの

mcp-demo/
├─ server.py
└─ client.py

serverは add(a,b) Toolと config://app Resourceを公開します。LLMは登場しません。まずMCPそのものが「モデル」ではなく「能力を発見・呼び出す規格」だと確認します。

1. 環境

Python SDK v2は現行stableです。

python -m venv .venv
.venv\Scripts\activate
pip install "mcp[cli]"

古い記事では FastMCP が出てきますが、Python SDK v2では高水準server classが MCPServer に変わっています。古いコードをそのまま混ぜないでください。

2. 最小serverを書く

server.py:

from mcp.server import MCPServer

mcp = MCPServer(
    "Demo",
    instructions="Use tools for calculations. Read config resources when configuration matters.",
)


@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two integers."""
    return a + b


@mcp.resource("config://app")
def app_config() -> str:
    """Return the demo application configuration."""
    return "environment=dev\nregion=ap-northeast-1\nread_only=true"

型注釈とdocstringからTool schemaが作られます。手でJSON Schemaを書く必要はありません。

3. Inspectorで触る

mcp dev server.py

表示されたURLを開き、Toolsから add を選び、a=10, b=32 を実行します。Resourcesから config://app も読めます。

ここで確認するのは、モデルがなくてもMCP serverが能力一覧とschema、実行結果を提供できることです。

4. Python Clientから呼ぶ

テストではnetworkを使わず、server objectへ直接Clientを接続できます。

client.py:

import anyio
from mcp import Client
from server import mcp


async def main():
    async with Client(mcp, raise_exceptions=True) as client:
        tools = await client.list_tools()
        print("TOOLS:", [t.name for t in tools.tools])

        result = await client.call_tool("add", {"a": 10, "b": 32})
        print("ADD:", result.structured_content or result.content)

        resource = await client.read_resource("config://app")
        print("RESOURCE:")
        for item in resource.contents:
            if hasattr(item, "text"):
                print(item.text)


anyio.run(main)

python client.py

本番ではURLによるStreamable HTTPやstdioなどへtransportを差し替えます。Client API側のTool呼び出しロジックは同じ考え方です。

5. ToolとResourceを分ける

ToolResource
意味処理・操作読み取る情報
例issue作成、検索、計算設定、文書、schema
副作用あり得る基本は読み取り
権限設計特に重要機密データ範囲が重要

「何でもTool」にせず、読み取り資料はResource、操作はToolという意味分けをすると、Agent側でも能力を理解しやすくなります。

6. 書き込みToolを追加して危険を確認する

次のようなToolを追加するときは、Toolのschemaだけで安全にはなりません。

@mcp.tool()
def delete_record(record_id: str) -> str:
    ...

認証・認可・監査・confirmationをserver側で持ちます。「モデルへ削除しないでと書く」は認可の代わりになりません。

7. Tool descriptionはAgentのroutingに効く

Tool名とdescriptionが曖昧だと、モデルはどれを呼ぶべきか迷います。

# 悪い
@mcp.tool()
def run(x: str): ...

# 良い
@mcp.tool()
def search_customer_orders(customer_id: str, limit: int = 20):
    """Return recent orders for one customer. Read-only."""

入力型、read-onlyか、対象範囲、limitなどをschemaで表現します。

8. MCPをAgentへ渡す前に単体テストする

LLMを挟む前にClientから次をテストします。

  • Tool一覧が期待通りか。
  • schemaが型どおりか。
  • 正常入力の結果。
  • 存在しないIDや不正入力。
  • 権限不足時のエラー。
  • timeout・外部API失敗。

AgentがToolを間違える問題と、MCP server自体が壊れている問題を分けられます。

9. v1の記事を読むときの注意

2026年現在、Python SDK v2がstableで、MCP protocolも2026-07-28 revisionへ進んでいます。v1の FastMCP や古いsession/handshake前提の記事は、そのままコピーせずmigration guideと現行docsを確認します。

10. 次に作る

  • SQLiteをread-only検索するToolを追加する。
  • HTTP serverとして起動し、別processからClientで接続する。
  • Toolごとの権限・監査ログを追加する。
  • 同じ能力を普通のfunction toolで実装し、MCP化の利点を比較する。
  • AI AgentへMCP serverを接続し、Tool選択をevalする。
