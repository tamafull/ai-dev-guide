AIの変更を「良くなった気がする」ではなく、同じ問題で比較する

Prompt、モデル、RAG、Tool、Agentを変えるたびに目視で数件試すだけでは、改善か悪化か判断できません。このページではJSONLのfixtureとPythonのgraderを作り、変更前後のpass率を自動比較します。

完成するもの

eval-lab/
├─ cases.jsonl
├─ app.py
└─ eval.py

題材は「問い合わせ分類」です。AIはcategory、urgent、reasonをJSONで返します。形式、category、urgentを決定論的に採点し、必要なら自由文reasonだけLLM graderへ回します。

1. fixtureを作る

cases.jsonl:

{"id":"billing-1","input":"身に覚えのない二重請求があります","category":"billing","urgent":true}
{"id":"billing-2","input":"先月の請求書を再発行したい","category":"billing","urgent":false}
{"id":"account-1","input":"知らない端末からログイン通知が来ました","category":"account","urgent":true}
{"id":"account-2","input":"メールアドレスを変えたい","category":"account","urgent":false}
{"id":"delivery-1","input":"予定日を3日過ぎても荷物が届かない","category":"delivery","urgent":true}
{"id":"delivery-2","input":"配送先住所を変更したい","category":"delivery","urgent":false}
{"id":"other-1","input":"サイトの文字を大きくしてほしい","category":"other","urgent":false}

実運用で失敗した入力をここへ追加していくと、回帰テストになります。

2. 評価対象のappを書く

app.py:

import json, os
from openai import OpenAI

client = OpenAI()
MODEL = os.getenv("OPENAI_MODEL", "gpt-6-astra")

PROMPT = """
問い合わせを分類する。
category: billing | account | delivery | other
urgent: 放置で金銭被害、安全性、期限超過の影響が拡大しそうならtrue。
JSONだけ返す:
{"category":"...","urgent":true,"reason":"..."}
"""


def predict(text):
    r = client.responses.create(
        model=MODEL,
        instructions=PROMPT,
        input=text,
    )
    return json.loads(r.output_text)

3. 決定論graderを書く

eval.py:

import json
from app import predict


def load_cases():
    with open("cases.jsonl", encoding="utf-8") as f:
        return [json.loads(line) for line in f if line.strip()]


def grade(case, output):
    return {
        "category": output.get("category") == case["category"],
        "urgent": output.get("urgent") is case["urgent"],
        "has_reason": isinstance(output.get("reason"), str) and len(output["reason"]) > 0,
    }


def main():
    rows = []
    for case in load_cases():
        try:
            output = predict(case["input"])
            scores = grade(case, output)
        except Exception as e:
            output = {"error": str(e)}
            scores = {"category": False, "urgent": False, "has_reason": False}

        rows.append((case, output, scores))
        print(case["id"], scores, output)

    for metric in ["category", "urgent", "has_reason"]:
        rate = sum(r[2][metric] for r in rows) / len(rows)
        print(metric, f"{rate:.1%}")


if __name__ == "__main__":
    main()

python eval.py

まずは「何件通ったか」を再現できるようにするだけで、prompt変更の比較がかなり楽になります。

4. 変更前後を保存する

結果をJSONへ保存し、commitごとに比較します。

results = {
    "model": MODEL,
    "prompt_version": "v3",
    "scores": {...},
    "failures": [...]
}

モデル名、prompt version、dataset versionを残さないと、後から「なぜ数字が変わったか」を追えません。

5. 平均点だけでなく失敗カテゴリを見る

90%→92%になっても、重要なsecurity caseだけ悪化していたら採用できません。caseへtagを付けます。

{"id":"account-1","tags":["security","urgent"], ...}

tag別にpass率を出すと、「全体は改善したがsecurityは悪化」のような変化が見えます。

6. 非決定性を扱う

同じ入力でも出力が揺れる場合は、各caseを複数回流します。

RUNS = 5

for case in cases:
    pass_count = 0
    for _ in range(RUNS):
        out = predict(case["input"])
        pass_count += int(grade(case, out)["category"])
    print(case["id"], pass_count / RUNS)

「5回中5回通る」のと「5回中3回通る」は、1回だけ見ればどちらも成功に見えることがあります。

7. LLM graderは最後の手段ではなく、適材適所

自由文の「分かりやすさ」「根拠の十分性」のようにルール化しにくい部分は、LLM graderを使えます。ただしgraderもモデルなので、grader自身を評価します。

まず20〜50件だけ人間が採点し、そのhuman labelとLLM graderの一致率を確認します。重要判定をgrader一発で自動承認しない方が安全です。

8. Agentではtrajectoryも評価する

最終回答だけ合っていても、危険なToolを呼んだり、無駄なloopを10回回していたら問題です。Agent evalでは次も記録します。

  • 正しいToolを使ったか。
  • Tool引数が正しいか。
  • 書き込み前に承認を取ったか。
  • 不要なToolを何回呼んだか。
  • 最終的なDB/ファイル状態が正しいか。
  • max turn内で終了したか。

9. Voice Agentは会話とtask outcomeを分ける

音声Agentは声が自然でも、裏側の予約や検索を間違えることがあります。会話品質、聞き取り、delegation、Tool実行、最終外部状態、ユーザーへの伝達を別々に測ります。OpenAIの2026年のVoice Agent評価ガイドも、transcriptや最終発話だけでは不十分としています。

10. Holdoutを作る

実装Agent自身が見ている10ケースだけに最適化すると、テストを満たすだけの挙動になることがあります。開発用fixtureと、最終判定用holdoutを分けます。

eval/
├─ dev.jsonl       # 開発中に見える
└─ holdout.jsonl   # 最終評価だけで使う

11. Evals APIの現在

2026年10月時点でOpenAIは従来のEvals platformを廃止移行中で、既存Evalsは10月31日にread-only、11月30日に終了予定と案内しています。新規の評価設計では、製品固有APIだけに依存せず、fixtureとgraderの考え方を自分のコード側にも残すと移行しやすくなります。

12. 発展課題

  • prompt v1/v2を自動で両方実行してdiff reportを出す。
  • latency、token、API費用もmetricへ追加する。
  • RAGならretrieval recallとanswer correctnessを分ける。
  • AgentならTool trajectoryをJSONへ保存する。
  • CIで重要caseが悪化したらmergeを止める。
