「AIに頼む」から、「失敗を見て自分で直すループ」を設計する

Loop Engineeringは、Agentが action → observation → validation → retry を繰り返し、成功条件を満たしたら止まる仕組みを設計する考え方です。ここでは、バグのあるPython関数をAIが修正し、pytestが通るまで最大3回だけ再試行する小さな修復ループを作ります。

完成するもの

loop-lab/
├─ calc.py
├─ test_calc.py
└─ repair_loop.py

AIへ「直して」と1回だけ頼むのではなく、実際のtest結果を観察として戻し、成功条件をpytestに固定します。最大試行回数、変更禁止、バックアップもコード側で管理します。

1. 壊れたコードとtestを用意する

calc.py:

def divide(a, b):
    return a // b

test_calc.py:

import pytest
from calc import divide


def test_normal():
    assert divide(5, 2) == 2.5


def test_zero():
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)


def test_negative():
    assert divide(-3, 2) == -1.5

pip install pytest openai
pytest -q

最初は失敗します。

2. ループの状態遷移を先に決める

START
  ↓
run tests
  ├─ pass → DONE
  └─ fail
       ↓
   collect source + failure log
       ↓
   ask model for candidate
       ↓
   validate candidate format
       ↓
   write candidate
       ↓
   run tests again
       ├─ pass → DONE
       └─ fail → retry until max_attempts

「何度か頑張って」ではなく、観察、成功判定、再試行、停止をコードにします。

3. repair loopを実装する

repair_loop.py:

import os
import shutil
import subprocess
from pathlib import Path
from openai import OpenAI

MODEL = os.getenv("OPENAI_MODEL", "gpt-6-astra")
MAX_ATTEMPTS = 3
TARGET = Path("calc.py")
BACKUP = Path("calc.py.bak")
client = OpenAI()


def run_tests():
    p = subprocess.run(
        ["pytest", "-q"],
        capture_output=True,
        text=True,
        timeout=30,
    )
    return p.returncode == 0, p.stdout + "\n" + p.stderr


def propose_fix(source, test_log):
    prompt = f"""
You are repairing exactly one Python file: calc.py.
Return ONLY the complete replacement contents of calc.py.
Do not modify tests. Do not add dependencies. Keep the public function name divide.

CURRENT FILE:
{source}

TEST OUTPUT:
{test_log}
"""
    r = client.responses.create(model=MODEL, input=prompt)
    return r.output_text.strip()


def candidate_is_allowed(text):
    forbidden = ["subprocess", "os.system", "pytest", "test_calc"]
    return all(x not in text for x in forbidden) and "def divide" in text


def main():
    if not BACKUP.exists():
        shutil.copy2(TARGET, BACKUP)

    for attempt in range(1, MAX_ATTEMPTS + 1):
        ok, log = run_tests()
        print(f"attempt={attempt} tests={'PASS' if ok else 'FAIL'}")
        print(log)
        if ok:
            print("DONE")
            return

        source = TARGET.read_text(encoding="utf-8")
        candidate = propose_fix(source, log)

        if not candidate_is_allowed(candidate):
            print("candidate rejected by policy")
            continue

        TARGET.write_text(candidate + "\n", encoding="utf-8")

    ok, log = run_tests()
    if ok:
        print("DONE")
    else:
        print("STOP: retry limit reached")
        shutil.copy2(BACKUP, TARGET)
        print("restored original file")


if __name__ == "__main__":
    main()

4. 実行する

set OPENAI_API_KEY=...
python repair_loop.py

うまくいけば、Agentが // を / へ修正し、次のtest実行で終了します。モデルが誤った修正を返しても、testが通らなければ次のloopへ進みます。

5. Promptではなくループ側が品質を作っている

この例で重要なのはpromptの文言より、外部の制御です。

  • 成功条件はモデル自己申告ではなくpytest。
  • 失敗logを次回のobservationとして戻す。
  • 最大3回で停止する。
  • test変更は禁止する。
  • 候補コードをpolicy checkする。
  • 失敗時は元ファイルへrollbackする。

「必ず正しく直してください」と強く書いても、この仕組みの代わりにはなりません。

6. Stop Criteriaを増やす

実務では回数だけでなく、次の条件でも止めます。

if estimated_cost > budget:
    stop("budget exceeded")

if same_failure_count >= 2:
    stop("same failure repeated")

if candidate_changes_public_api:
    stop("requires human decision")

if touches_production_credentials:
    stop("forbidden capability")

Agentが「続けられる」ことと「続けてよい」ことは別です。

7. Observationをそのまま全部戻さない

test logが数万行になった場合、全量を毎回Contextへ戻すとコストとノイズが増えます。まず失敗test名、例外、stack trace周辺だけ抽出し、原ログへのpathを残します。

OBSERVATION = {
    "failed_tests": ["test_normal", "test_negative"],
    "error": "expected 2.5 but got 2",
    "full_log": "artifacts/pytest-002.log"
}

これはContext Engineeringともつながります。

8. 同じ失敗を繰り返したら戦略を変える

ただ再実行するだけでは「retry loop」であって、賢いloopではありません。2回同じ失敗なら、次のactionを変えます。

  • 追加の関連ファイルを読む。
  • 別の仮説を要求する。
  • 強いモデルへ切り替える。
  • 人間へ判断を戻す。

failure signatureを保存して、同じerror textや同じtest failureが続いた回数を数えられます。

9. Loopを評価する

5〜20個の壊れた関数を用意し、次を記録します。

  • 1回目で直った割合。
  • 3回以内で直った割合。
  • 平均試行回数。
  • testを壊そうとした回数。
  • rollback回数。
  • 成功1件あたりのtoken / API費用。

「1回の回答品質」ではなく、loop全体で成功までに使った資源を見るのがポイントです。

「Loop Engineering」という言葉について

これはPrompt Engineeringほど確立した古い用語ではなく、2026年にIBMなどがagentic workflowの反復設計を表す言葉として使っている新しい呼称です。重要なのは名前より、Agentの行動、観察、検証、再試行、停止を明示的に設計する考え方です。
