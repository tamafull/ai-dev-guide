ローカルLLMを動かし、量子化で何が変わるか測る

量子化は、モデル重みをより少ないbit数で表現し、ファイルサイズや必要メモリを減らす方法です。このページではllama.cppでGGUFモデルを実際に起動し、速度、メモリ、出力品質、context長のトレードオフを確認します。

完成するもの

小型instruction modelをPC上で起動し、同じpromptを複数量子化で実行して比較表を作ります。

local-llm/
├─ prompts.txt
└─ results.md

1. llama.cppを用意する

llama.cppはWindows/macOS/Linux向けのprebuilt binary、package manager、source buildなど複数の導入方法があります。インストール後、次が通ることを確認します。

llama-cli --help
llama-server --help

最近のllama.cppではHugging Face上の対応GGUFを -hf から直接取得して実行できます。

2. まず1B級モデルを起動する

公式ドキュメントにも掲載されているGGUF repoの例です。

llama-cli -hf ggml-org/gemma-3-1b-it-GGUF

初回はmodelをdownloadし、以後cacheを使います。1B級なら大規模モデルより必要メモリが小さく、ローカルLLMの挙動を試しやすいです。

3. 一問だけ実行して速度を見る

llama-cli -hf ggml-org/gemma-3-1b-it-GGUF -st -p "量子化とは何かを150字以内で説明して"

実行末尾のtiming情報からprompt processingとgenerationのtokens/secを記録します。CPU/GPU、backend、context、model sizeで大きく変わるので、他人のtokens/secより自分のPCで測る方が重要です。

4. samplingを変える

llama-cli -hf ggml-org/gemma-3-1b-it-GGUF --temp 0.2 --top-k 40 --top-p 0.95

temperatureを下げると候補選択が保守的になります。これはモデル自体の知識や精度を増やす設定ではありません。

5. contextを増やすとメモリも増える

llama-cli -hf ggml-org/gemma-3-1b-it-GGUF -c 4096
llama-cli -hf ggml-org/gemma-3-1b-it-GGUF -c 16384

モデル重みだけでなくKV cacheにもメモリが必要です。「model fileがRAMに入るから動く」とは限りません。長いcontextを使うと追加メモリが必要になります。

6. 量子化違いを比較する

同じmodelのGGUF repoにQ8、Q6、Q5、Q4など複数量子化がある場合、同じpromptをそれぞれで試します。repoにある正確なfile/quant名を確認して選んでください。

llama-cli -hf USER/MODEL-GGUF:Q8_0 -st -p "TCPとUDPの違いを説明して"
llama-cli -hf USER/MODEL-GGUF:Q4_K_M -st -p "TCPとUDPの違いを説明して"

比較表を作ります。

quantfile sizeRAM/VRAMtok/s回答品質
Q8記録記録記録5問で採点
Q4_K_M記録記録記録同じ5問

量子化は小さいほど常に速いわけではありません。backendやhardwareによって計算効率が違います。品質もmodel・taskによって落ち方が違うため、固定promptで比較します。

7. 自分で量子化する流れ

llama.cppでは、Hugging Face形式のmodelをGGUFへ変換し、高精度GGUFから低bit GGUFへquantizeできます。

git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
python -m pip install -r requirements.txt

python convert_hf_to_gguf.py PATH_TO_MODEL --outfile model-f16.gguf
# binary名はbuild/releaseに合わせる
llama-quantize model-f16.gguf model-q4_k_m.gguf Q4_K_M

実際のscript名やbinary pathはllama.cppの現行docs/buildで確認してください。モデルによって変換対応状況も異なります。

8. なぜ4bitで約1/4になるとは限らないのか

重み本体は小さくなりますが、GGUFにはmetadataやTokenizer情報が入り、推論時にはKV cache、runtime buffer、GPU/CPU workspaceも必要です。したがって「7B × 4bit = 3.5GBだから4GB RAMで必ず動く」とは計算できません。

9. OpenAI互換serverとして使う

llama-server -hf ggml-org/gemma-3-1b-it-GGUF

local HTTP serverとして起動すれば、自作アプリからモデル呼び出し部分だけ差し替えやすくなります。RAGやAgentの実験で、cloud API版とlocal版を同じevaluationへ通すこともできます。

10. モデル選びで見るもの

  • parameter数だけでなく、実際のbenchmarkと自分のtask。
  • licenseと商用利用条件。
  • context length。
  • 日本語・code・tool useなど必要能力。
  • GGUF対応とchat template。
  • quantizationごとの品質差。

11. 「低スペックPCで壊れる？」

通常は、必要メモリを超えればallocation failure、極端なswapで非常に遅くなる、GPU OOMになる、といった形で失敗します。モデルを動かしたこと自体でPCが物理的に壊れるのが通常の挙動ではありません。ただし高負荷が長時間続くため、冷却不良や不安定なoverclockなど元々のhardware問題は顕在化し得ます。

12. 発展課題

  • 1B / 4B / 8B級で同じ10問を評価する。
  • Q8 / Q6 / Q5 / Q4で品質と速度を比較する。
  • CPU onlyとGPU offloadを比較する。
  • context 4k / 16k / 32kでメモリ使用量を記録する。
  • RAGをlocal modelへ接続し、cloud API版と比較する。
