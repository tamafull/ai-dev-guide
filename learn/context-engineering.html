Context Engineeringを、実際に「詰め込み方式」と比較して理解する

Context Engineeringは、良い一文を書く技術ではありません。モデルが判断する瞬間に、どの指示・資料・状態・ツール結果を見せるかを設計する技術です。このページでは同じ5問を「全資料を毎回入れる方式」と「必要資料だけ取る方式」で実行し、正答率と入力tokenを比較します。

この記事で作るもの

架空の社内ヘルプデスクを題材に、次の2方式を作ります。

  1. stuff-all: 規約、手順、FAQ、運用メモを毎回すべてpromptへ入れる。
  2. just-in-time: 常時必要なルールだけ固定し、質問に関係する資料だけ検索して追加する。

最後に同じ評価セットで、正答率・参照資料・入力token数を比較します。

1. Contextに含まれるものを分解する

会話履歴だけがContextではありません。Agentでは少なくとも次が候補になります。

種類例基本方針
高優先度の指示役割、禁止事項、出力契約短く安定させる
今回の入力質問、Issue、依頼内容必ず入れる
資料仕様、FAQ、設計書必要時に取得
作業状態決定事項、未完了、エラー構造化して持つ
会話履歴過去turn長期化したら圧縮
ツール定義API schema、MCP tools必要な能力だけ見せる
ツール結果検索結果、ログ、SQL結果要点と原データへの参照を分ける

「何を知っているAIか」ではなく、「今この呼び出しで何が見えているか」を考えるのが出発点です。

2. 実験用プロジェクトを作る

context-lab/
├─ docs/
│  ├─ password.md
│  ├─ billing.md
│  ├─ vpn.md
│  ├─ devices.md
│  └─ deprecated.md
├─ policy.md
├─ eval_cases.json
└─ compare.py

policy.md は毎回必要な短いルールだけにします。

# Support policy
- 回答は与えられた資料だけを根拠にする。
- 不明なら「確認できません」と答える。
- `deprecated.md` の内容は、現行資料と矛盾する場合に採用しない。
- 回答末尾に参照したファイル名を付ける。

docs/password.md:

# Password
パスワード再設定は /account/reset から行う。
再設定メールの有効期限は30分。

docs/deprecated.md には意図的に古い情報を入れます。

# Old manual
旧システムではパスワード再設定メールの有効期限は24時間だった。
この文書は2024年に廃止済み。

残りの文書にも、請求、VPN、端末登録など別テーマの短い情報を書きます。

3. まず悪い例: 全資料を毎回入れる

from pathlib import Path

def stuff_all(question):
    policy = Path("policy.md").read_text(encoding="utf-8")
    docs = []
    for p in Path("docs").glob("*.md"):
        docs.append(f"FILE={p.name}\n{p.read_text(encoding='utf-8')}")
    return f"{policy}\n\nQUESTION:\n{question}\n\nDOCUMENTS:\n" + "\n\n---\n\n".join(docs)

5ファイル程度ならまだ動きます。しかし実際のリポジトリや社内Wikiが100〜10000ファイルになると、入力tokenが増えるだけでなく、古い資料・似た規約・無関係なログが同時に見えるようになります。

4. 必要資料だけ取る

検索自体は簡易実装で構いません。ここでは文書ごとにEmbeddingを作ります。

pip install sentence-transformers numpy openai tiktoken

import numpy as np
from pathlib import Path
from sentence_transformers import SentenceTransformer

embedder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
paths = list(Path("docs").glob("*.md"))
texts = [p.read_text(encoding="utf-8") for p in paths]
vectors = embedder.encode(texts, normalize_embeddings=True)


def retrieve(question, k=2):
    q = embedder.encode([question], normalize_embeddings=True)[0]
    scores = vectors @ q
    order = np.argsort(scores)[::-1][:k]
    return [(float(scores[i]), paths[i], texts[i]) for i in order]


def just_in_time(question):
    policy = Path("policy.md").read_text(encoding="utf-8")
    results = retrieve(question)
    docs = [f"FILE={p.name} SCORE={score:.3f}\n{text}" for score, p, text in results]
    return f"{policy}\n\nQUESTION:\n{question}\n\nRELEVANT DOCUMENTS:\n" + "\n\n---\n\n".join(docs)

重要なのはEmbedding自体ではなく、資料を常時Contextへ載せず、必要になった時に選ぶ点です。検索手段はkeyword、DB、MCP、専用APIでも構いません。

5. token量を測る

import tiktoken

enc = tiktoken.get_encoding("o200k_base")

def token_count(text):
    return len(enc.encode(text))

q = "パスワード再設定メールは何分有効？"
print("stuff-all", token_count(stuff_all(q)))
print("jit", token_count(just_in_time(q)))

実際の利用モデルとTokenizerが違えばtoken数も変わるので、これは比較用の概算です。文書数を50、500と増やして差を見ると、static stuffingの伸び方が分かります。

6. 同じモデルで回答品質を比較する

import os
from openai import OpenAI

client = OpenAI()
MODEL = os.getenv("OPENAI_MODEL", "gpt-6-astra")


def ask(context):
    r = client.responses.create(
        model=MODEL,
        input=context,
    )
    return r.output_text

eval_cases.json:

[
  {"q":"パスワード再設定メールは何分有効？","must":"30分","source":"password.md"},
  {"q":"VPNが使えないとき最初に何を確認する？","must":"証明書","source":"vpn.md"},
  {"q":"請求書はいつ発行される？","must":"毎月1日","source":"billing.md"},
  {"q":"新しいPCを登録するには？","must":"端末登録","source":"devices.md"},
  {"q":"社用スマホの紛失補償はいくら？","must":"確認できません","source":null}
]

評価コードでは、両方式で同じquestionを実行し、must が含まれるか、正しいsourceを挙げたか、入力tokenが何個かを記録します。

import json

cases = json.loads(Path("eval_cases.json").read_text(encoding="utf-8"))

for mode, builder in [("all", stuff_all), ("jit", just_in_time)]:
    ok = 0
    total_tokens = 0
    print("\n===", mode, "===")
    for c in cases:
        ctx = builder(c["q"])
        ans = ask(ctx)
        passed = c["must"] in ans
        ok += int(passed)
        total_tokens += token_count(ctx)
        print("OK" if passed else "NG", c["q"], "tokens=", token_count(ctx))
        print(ans)
    print("accuracy", ok / len(cases), "total_input_tokens", total_tokens)

小さな例では正答率が同じこともあります。その場合でも入力tokenが下がれば、規模を大きくした時の余裕が増えます。一方、検索が悪く正答率が落ちるなら、Context Engineeringの改善点はpromptではなくretrievalです。

7. 「古い正本」が混ざる問題を作ってみる

deprecated.md の24時間と、現行 password.md の30分を同時にstuff-allへ入れます。モデルが正しく優先できる場合もありますが、規模が大きくなると「どれが現在の正本か」という情報自体が重要になります。

改善方法は単純です。

  • 廃止文書を検索対象から外す。
  • status=active、valid_from などmetadataを持つ。
  • 現行資料を先にfilterしてからsemantic searchする。
  • 正本URLやdocument IDをContextへ残す。

8. 長時間タスクでは「会話履歴」と「状態」を分ける

100turnの会話をそのまま状態管理に使うと、「何が決定済みか」を探すために古い会話全部が必要になります。代わりに、作業状態を構造化して外へ出します。

{
  "goal": "顧客データ移行を完了する",
  "decisions": [
    "旧API互換を維持する",
    "削除処理は今回の対象外"
  ],
  "done": ["schema調査", "migration案"],
  "next": ["staging検証"],
  "blocked": [],
  "evidence": ["CI #1842", "benchmark.csv"]
}

会話は圧縮しても、この状態ファイルはそのまま残せます。Anthropicが長時間Agent向けに挙げているcompaction、structured memory、sub-agent architectureも、Contextを有限資源として扱う同じ発想です。

9. Tool定義もContextを使う

100個のTool schemaを毎回モデルへ見せると、入力tokenだけでなく選択肢も増えます。常時必要なToolと、必要時に探索するToolを分けます。

例:

通常: search_docs, read_file, save_note
DB作業を検知したら追加: schema, query_readonly
デプロイ作業を検知したら追加: ci_status, deploy_preview

「使える能力を増やす」と「常に全能力をContextへ入れる」は別問題です。

10. Sub-AgentはContext分離にも使える

補助Agentの利点は並列化だけではありません。巨大なログ調査を別Agentに渡し、主Agentへ「重要な5件＋原文参照」だけ返せば、主Contextを汚さず探索できます。

ただし要約だけ残すと証拠が消えるので、元ファイル、行番号、URL、tool result IDなどへ戻れる参照を持たせます。

11. Context設計の失敗パターン

症状疑う場所
長くなるほど指示を忘れる会話履歴・重複資料・古いログの詰め込み
古い仕様を使う正本metadata、retrieval filter
Tool選択をよく間違えるTool数、schema名、説明、遅延ロード
compact後に条件が落ちる重要状態を会話外へ保存しているか
sub-agentの結論を検証できない要約だけでなく原データ参照を残しているか
入力tokenだけ下げたら精度も落ちた削りすぎ。成功率との両方で評価する

12. 実運用で測る指標

Context Engineeringを「token削減テクニック」だけにすると失敗します。少なくとも次を同時に見ます。

  • task success rate
  • 入力token / 成功1件
  • retrieval hit rate
  • 誤った古い資料の参照率
  • tool選択ミス
  • 再試行回数
  • 人間の修正時間

JIT retrievalでtokenが半分になっても、正答率が落ちて再試行が倍なら改善とは言えません。
