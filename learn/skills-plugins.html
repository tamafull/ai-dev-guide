繰り返す手順をSkillにし、必要ならPluginとして配布する

Skillは「どう進めるか」を再利用する単位、PluginはSkillやMCP serverなどをまとめて配布する単位です。このページでは会議準備Skillを実際に作り、trigger、手順、テンプレート、失敗条件を定義します。

完成するもの

meeting-prep/
├─ SKILL.md
├─ references/
│  └─ brief-format.md
└─ scripts/
   └─ validate_brief.py

Skillは「会議準備」という1つのjobだけに絞ります。GmailやCalendarのような外部能力はSkill自身へ埋め込まず、利用可能なPlugin/MCP Toolへ依存する設計にします。

1. 最小SKILL.mdを書く

Skillはフォルダ内の SKILL.md を中心に構成します。

---
name: meeting-prep
description: Prepare a source-linked meeting brief from calendar events, messages, and notes. Use when the user asks to prepare for an upcoming meeting. Do not use for meeting minutes after the meeting.
---

Prepare a meeting brief.

1. Identify the target meeting and its date/time.
2. Find the latest relevant source material available through connected tools.
3. Separate confirmed facts from missing information.
4. Use `references/brief-format.md` for the output structure.
5. Link or name every source used.
6. Do not create, edit, or send calendar events or messages unless the user explicitly asks.
7. If the meeting cannot be uniquely identified, stop and report what is ambiguous.

description は説明文ではなくrouting情報でもあります。「いつ使うか」と「いつ使わないか」を短く入れます。

2. 出力テンプレートを別ファイルにする

references/brief-format.md:

# Meeting brief

## Objective

## Participants

## Current facts

## Decisions already made

## Risks / open questions

## Suggested questions

## Sources

長いテンプレートや背景資料をSKILL.md本体へ全部入れず、必要になったときだけ読む形にするとSkill一覧のContextを軽く保てます。

3. 決定論的な検証はscriptへ出す

scripts/validate_brief.py:

from pathlib import Path
import sys

required = [
    "## Objective",
    "## Participants",
    "## Current facts",
    "## Risks / open questions",
    "## Sources",
]

text = Path(sys.argv[1]).read_text(encoding="utf-8")
missing = [x for x in required if x not in text]

if missing:
    print("missing:", missing)
    raise SystemExit(1)

print("brief structure: OK")

見出しの存在確認までLLMへ自己採点させる必要はありません。決定論的に判定できる部分はscriptへ出します。

4. triggerをテストする

良いSkillは手順だけでなく、呼ばれる範囲が適切です。次のpromptで期待する挙動を決めます。

Prompt期待
「明日のAcme会議の準備をして」trigger
「来週の1on1用に関連メモを整理して」trigger候補
「今日の会議の議事録を書いて」triggerしない
「会議を木曜14時に作って」meeting-prepではなくCalendar操作

Skillを増やすほどdescription同士の境界が重要になります。

5. SkillとSystem Promptを分ける

毎turn必ず守る短い安全ルールはglobal instruction側、特定jobだけで使う長い手順はSkillへ置きます。

置き場所例
Global instruction秘密情報を公開しない、破壊操作は承認必須
Skill会議準備、リリースノート、PR review手順
Tool / MCPメール検索、Calendar取得、Issue更新
Referenceテンプレート、社内規約、判断表
Scriptlint、CSV整形、検証、変換

6. Pluginとの境界

Pluginはinstall可能なbundleで、Skillだけでも、Skill＋MCP serverでも構成できます。

Plugin
├─ Skills
│  └─ meeting-prep/
│     ├─ SKILL.md
│     └─ references/...
└─ MCP server (optional)
   ├─ search_email
   └─ get_calendar_event

MCP serverは認証、認可、live data、actionを提供し、Skillはそれらをどう組み合わせるかを説明します。

7. Skillを作る前に一度手で成功させる

曖昧なworkflowを先にSkill化すると、曖昧さが固定されます。

  1. 普通の会話で1件成功させる。
  2. どの入力・資料・判断が必要だったか記録する。
  3. 再利用部分だけSKILL.mdへ抽出する。
  4. triggerとnon-trigger promptを用意する。
  5. 別の会議で再実行する。

現在のChatGPT/OpenAIの公式ガイドでも、「まず1回やる→方法を保存→別入力で再利用→改善」という流れが推奨されています。

8. Contextを増やさないSkill設計

Skillはprogressive disclosureで使われます。最初はname/descriptionなどのmetadataだけが見え、選択された後にSKILL.md本体、さらに必要ならreferences/scriptsを読みます。

そのため、descriptionへ詳細手順を全部書かず、trigger判断に必要な情報だけをfront-loadします。

9. セキュリティ

Skillは命令とscriptを持てるため、信頼できないSkillを高権限Toolと組み合わせると危険です。install前に次を確認します。

  • scriptがどのファイル・networkへ触るか。
  • MCP/tool依存が何を許可するか。
  • 秘密情報を外部へ送る手順がないか。
  • 暗黙triggerが広すぎないか。
  • 破壊操作前の承認があるか。

10. 次に作るSkill

  • PR review: diff→risk分類→test確認→review template。
  • research: search→一次情報確認→反証検索→出典付き要約。
  • study-note: 資料→問題生成→回答→弱点記録。
  • incident-summary: logs→timeline→impact→unknown→next action。

各Skillは「何でもできる万能Skill」ではなく、1つのjobに狭く保つ方がtriggerと評価がしやすくなります。
