Prompt Engineeringを「うまい文章」ではなく、測れる変更として扱う

良いpromptは長いpromptとは限りません。目的、判断基準、禁止事項、出力契約を必要なだけ書き、固定した入力セットで変更前後を比べます。このページでは問い合わせ分類を題材に、v1とv2のpromptをA/Bテストします。

完成するもの

10件の問い合わせを billing / account / delivery / other に分類し、urgencyも返す小さなプログラムを作ります。評価するのは「JSONとして読めるか」「categoryが正しいか」「余計な文章を出さないか」です。

1. 環境

python -m venv .venv
.venv\Scripts\activate
pip install openai
set OPENAI_API_KEY=...

APIモデルは環境変数 OPENAI_MODEL で差し替えられるようにします。

2. 評価セットを先に作る

prompt_ab.py:

CASES = [
    ("二重に請求されています", "billing", True),
    ("請求書をPDFでほしい", "billing", False),
    ("パスワードを忘れました", "account", False),
    ("アカウントを乗っ取られたかもしれない", "account", True),
    ("荷物が予定日を過ぎても届かない", "delivery", True),
    ("配送先住所を変更したい", "delivery", False),
    ("料金プランについて知りたい", "billing", False),
    ("メールアドレスを変えたい", "account", False),
    ("商品ページが見づらい", "other", False),
    ("こんにちは", "other", False),
]

promptを書く前に「何を正解とするか」を固定すると、都合のいい成功例だけを見て改善した気になるのを防げます。

3. v1: 曖昧なprompt

PROMPT_V1 = """
問い合わせを分類してください。
categoryとurgencyをJSONで返してください。
"""

人間には意味が通じますが、category候補、urgencyの判断基準、JSON以外を禁止するかが曖昧です。

4. v2: 判断契約を明示する

PROMPT_V2 = """
あなたは問い合わせ分類器です。

categoryは必ず次のどれか:
- billing: 請求、料金、支払い、請求書
- account: ログイン、パスワード、メール変更、アカウント安全性
- delivery: 発送、到着、配送先、追跡
- other: 上記以外

urgentは、金銭被害・不正アクセス疑い・期限超過など、
放置で被害が拡大する可能性が高い場合だけtrue。

次のJSONだけを返す。説明文やMarkdownは禁止。
{"category":"billing|account|delivery|other","urgent":true|false}
"""

5. 同じ10件を両方へ流す

import json, os
from openai import OpenAI

client = OpenAI()
MODEL = os.getenv("OPENAI_MODEL", "gpt-6-astra")


def classify(prompt, text):
    r = client.responses.create(
        model=MODEL,
        instructions=prompt,
        input=text,
    )
    return r.output_text.strip()


def evaluate(prompt):
    valid_json = 0
    category_ok = 0
    urgent_ok = 0
    rows = []

    for text, expected_cat, expected_urgent in CASES:
        raw = classify(prompt, text)
        try:
            obj = json.loads(raw)
            valid_json += 1
            cat_ok = obj.get("category") == expected_cat
            urg_ok = obj.get("urgent") is expected_urgent
            category_ok += int(cat_ok)
            urgent_ok += int(urg_ok)
            rows.append((text, raw, cat_ok, urg_ok))
        except json.JSONDecodeError:
            rows.append((text, raw, False, False))

    n = len(CASES)
    return {
        "json_rate": valid_json / n,
        "category_accuracy": category_ok / n,
        "urgent_accuracy": urgent_ok / n,
        "rows": rows,
    }

for name, prompt in [("v1", PROMPT_V1), ("v2", PROMPT_V2)]:
    result = evaluate(prompt)
    print(name, {k: v for k, v in result.items() if k != "rows"})
    for row in result["rows"]:
        if not row[2] or not row[3]:
            print("  NG", row)

1回の結果だけで差が小さい場合は、各caseを複数回実行してばらつきも見ます。生成AIは非決定的なので、10件×1回より10件×5回の方が安定性を判断しやすくなります。

6. Promptを直す順番

失敗ごとに原因を分けます。

失敗先に直す場所
JSONの前後に説明を書く出力契約・Structured Outputs
billingとaccountを混同分類境界とfew-shot例
urgentを何でもtrueにする判断基準・反例
資料にない事実を補う根拠範囲・不明時の挙動
長いタスク途中で目的を失うPromptよりContext/Loop設計

7. Few-shotは「難しい境界」に使う

例を大量に貼る前に、モデルが迷う境界だけ追加します。

EXAMPLES = """
例:
入力: 料金が高いので退会したい
出力: {"category":"billing","urgent":false}

入力: 知らない端末からログイン通知が来た
出力: {"category":"account","urgent":true}
"""

代表例より「間違えやすい反例」を入れる方が効く場合があります。

8. Promptに書かない方がよいもの

変化する大量データ、長い社内規定、ツール出力全部、過去ログ全部をpromptへ詰めると、重要な指示が埋もれます。必要な情報を必要な時だけ取得するのはContext Engineeringの範囲です。

また、本番promptは文字列を管理画面で手修正するだけにせず、コードと同様にversion管理し、fixtureとevalを一緒に変更するとrollbackしやすくなります。OpenAIの2026年のAPIガイドでもproduction promptをcode-managedにする方向が案内されています。

9. 発展実験

  • v2を短く削り、精度が落ちない最小promptを探す。
  • few-shot 0 / 2 / 10件で精度と入力tokenを比較する。
  • 別モデルでも同じ評価セットを流す。
  • JSON schemaによるStructured Outputsを使い、形式失敗をpromptから分離する。
  • 誤分類だけを集め、回帰テストへ追加する。
