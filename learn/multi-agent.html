複数Agentに分ける前に、単一Agentより本当に得か測る

Multi-AgentはAgentを増やすこと自体が目的ではありません。独立した探索を分け、最後の統合責任を明確にするための設計です。このページでは「顧客会議の準備」を単一Agent版とManager＋2 Specialist版で実行し、時間・Tool呼び出し・出力の抜けを比較します。

完成する構成

               ┌─ customer specialist
user → manager ┤
               └─ risk specialist
                        ↓
                  managerが統合

Specialistは最終回答を直接返さず、ManagerからToolとして呼ばれます。OpenAI Agents SDKでいう agents as tools パターンです。

1. 環境

pip install openai-agents
set OPENAI_API_KEY=...

2. Specialistを作る

multi.py:

import time
from agents import Agent, Runner

customer_agent = Agent(
    name="Customer specialist",
    instructions="""
顧客メモを読み、顧客の要望、期限、未解決事項だけを抽出する。
推測を足さない。
""",
)

risk_agent = Agent(
    name="Risk specialist",
    instructions="""
与えられた情報から、技術リスク、運用リスク、確認が必要な点を抽出する。
事実と推測を分ける。
""",
)

3. ManagerへAgentをToolとして渡す

manager = Agent(
    name="Meeting manager",
    instructions="""
顧客会議のブリーフを作る。
必要ならspecialistを使う。
最終出力は 目的 / 顧客要望 / 現状 / リスク / 質問 の順。
同じ内容を重複させない。
""",
    tools=[
        customer_agent.as_tool(
            tool_name="analyze_customer",
            tool_description="顧客要望・期限・未解決事項を抽出する",
        ),
        risk_agent.as_tool(
            tool_name="analyze_risks",
            tool_description="技術・運用リスクと確認事項を抽出する",
        ),
    ],
)

4. 単一Agentも用意する

single = Agent(
    name="Single meeting agent",
    instructions="""
顧客会議のブリーフを作る。
目的 / 顧客要望 / 現状 / リスク / 質問 の順で整理し、推測は明示する。
""",
)

INPUT = """
顧客Acme。契約更新は11月末。
CSV exportは現在8分で、顧客目標は2分以内。
11月第2週にstaging予定。
10/18にexport worker遅延。原因はqueue backlog。
worker scalingとquery見直しが恒久対策候補。
"""


def run(agent):
    start = time.perf_counter()
    result = Runner.run_sync(agent, INPUT)
    elapsed = time.perf_counter() - start
    return result.final_output, elapsed

for name, agent in [("single", single), ("multi", manager)]:
    text, sec = run(agent)
    print("\n===", name, f"{sec:.2f}s ===")
    print(text)

Multi-Agentは呼び出しが増えるため、普通はlatencyとtoken消費も増えます。出力が少し良いだけなら割に合わない可能性があります。

5. 「良かった気がする」をやめて採点する

最低限のrubricを作ります。

CHECKS = [
    "11月末",
    "8分",
    "2分",
    "11月第2週",
    "queue backlog",
]


def score(text):
    return sum(x in text for x in CHECKS) / len(CHECKS)

同じ入力を5回ずつ流し、平均score、平均時間、失敗例を記録します。Multi-Agentは非決定的なroutingも増えるため、1回だけの比較では判断しません。

6. Multi-Agentが効く分割

並列化しやすいのは、互いの途中結果を待たずに進められる仕事です。

  • 別々の情報源を探索する。
  • 複数案を独立に作る。
  • 実装と独立reviewを分ける。
  • セキュリティ・性能・互換性など観点を分ける。

一方、「設計Agent→実装Agent→テストAgent」のように直列依存するだけなら、Agentを分けるほどhandoffで情報が落ちることがあります。

7. HandoffとAgents as toolsを使い分ける

方式誰が最終回答を持つか向くケース
Agents as toolsManager専門家の結果を統合したい
Handoff移譲先Agent専門家へ会話自体を引き継ぎたい

「旅行調査Agent」「価格調査Agent」の結果を1つの提案へ統合するならManager型、問い合わせを「技術窓口」「請求窓口」へそのまま振り分けるならhandoffが自然です。

8. 本当に並列化する

LLMにroutingさせず、独立作業だと分かっているならPython側で並列実行できます。

import asyncio
from agents import Runner

async def gather():
    a, b = await asyncio.gather(
        Runner.run(customer_agent, INPUT),
        Runner.run(risk_agent, INPUT),
    )
    return a.final_output, b.final_output

customer_result, risk_result = asyncio.run(gather())

その2結果だけをManagerへ渡せば、探索は並列、統合は一箇所にできます。固定workflowなら、すべてをLLM routingに任せる必要はありません。

9. 共有状態を決める

複数Agentがファイルを編集する場合、メッセージだけで協調させると競合します。少なくとも担当範囲、完了状態、編集権、決定事項を共有します。

{
  "tasks": {
    "api": {"owner":"agent-a", "status":"doing"},
    "tests": {"owner":"agent-b", "status":"todo"}
  },
  "locked_files": ["schema.sql"],
  "decisions": ["public APIは変更しない"]
}

10. 比較すべきコスト

Multi-Agentの評価ではモデルAPI料金だけでなく、統合失敗や重複も含めます。

  • task success rate
  • wall-clock time
  • 総token / API費用
  • 同じ情報を重複調査した回数
  • 統合時に矛盾した回答数
  • 人間のreview時間

11. 発展課題

  • customer/risk/performanceの3Agentへ増やす。
  • singleとmultiを20ケースで比較する。
  • Agentを増やすほど品質がどこで頭打ちになるか測る。
  • 並列探索だけmultiにし、ファイル書き換えはManagerだけに限定する。
  • specialistの結果に根拠URLやfile pathを必須にする。
