コンテキスト設計 · 2026-10-26

AIに渡す情報は、量より「いつ必要か」で設計する

最初から全部を読ませません。AGENTS.mdやCLAUDE.mdには毎回必要なルールだけを置き、詳しい手順や背景は別ファイルへ分けます。AIには必要になった時点でそのファイルを読ませます。

推奨信頼度: 中〜高

AGENTS.mdやCLAUDE.mdは「百科事典」ではなく入口にする

毎回守るルールだけを入口ファイルへ置きます。個別機能の設計や長い運用手順は、必要なときだけ読む別文書へ分けます。

AGENTS.md

・プロジェクト標準の初期化、テスト、静的解析コマンドを使う。
・既存のアーキテクチャ境界を崩さない。
・公開APIや永続データ形式を変える場合は、実装前に影響範囲を報告する。
・認証/認可を変更する場合は docs/auth.md を読む。
・DB変更は docs/database-migrations.md を読む。

入口側には「何を常に守るか」と「どの作業でどの文書を読むか」だけを書きます。これは言語やフレームワークが変わっても同じです。

プロジェクト固有コマンドの例

コマンド自体は言語・ビルド環境に合わせます。代表例を切り替えて見られます。

bundle exec rspec
bundle exec rubocop

Railsなら bin/rspec、bin/rubocop のようなwrapperがあればそちらを優先します。

python -m pytest
ruff check .
python -m mypy src
npm test
npm run lint
npm run typecheck

pnpm / yarn / bun を使う場合はプロジェクト標準に合わせます。

./gradlew test
./gradlew check

Mavenなら ./mvnw test などへ置き換えます。

go test ./...
go vet ./...
cargo test
cargo clippy --all-targets --all-features
cmake -S . -B build
cmake --build build
ctest --test-dir build

MakeやMesonを使う場合は、そのプロジェクトの標準コマンドを書きます。

大事なのはコマンド名そのものではなく、AIが毎回「このリポジトリでは何を実行するのか」を推測しなくてよい状態にすることです。

この構造にする理由は、AIが一度に扱えるコンテキストが有限だからです。Anthropicは必要な情報を選別することをコンテキスト設計の中心に置いています。GoogleのADK事例でも、リポジトリ規約をSkillへ分け、短い入口から必要な参考文書だけを読む構成を使っています。

AGENTS.mdは正解率を上げる「追加知能」とは考えない

AGENTS.mdの主な役割は、難しい実装問題を解けるようにすることではなく、リポジトリ固有の手順や禁止事項を安定して伝えることです。

2026年10月のREALM 2026で発表された研究は、Claude CodeとCodexを3リポジトリ・17タスク・288評価runで比較しました。コンテキストファイルなし、AGENTS.md相当の情報を与える条件、必要時に参照できる条件を比べても、実装正解率に測定可能な差は出ませんでした。失敗の中心は、機能設計や既存パターンの選択、正確な実装といった能力側でした。

そのため、知識を大量に詰めて「モデルを賢くする」より、ビルド方法、テスト方法、禁止事項、詳細文書への入口を短く置きます。ルール違反を確実に止めたい場合は、CI、lint、構造テストでも強制します。

AGENTS.mdの効果を検証した研究と、実務での使いどころを詳しく読む →

詳しい知識は「必要になったら読む」形に分ける

長い設計資料を1つの指示ファイルへ詰め込まず、仕事の種類ごとに分けます。

AGENTS.md
├ 認証・認可を変更する → docs/auth.md
├ DBを変更する → docs/database-migrations.md
├ 公開APIを変更する → docs/api-compatibility.md
├ 非同期処理を変更する → docs/jobs.md
└ 性能調査をする → docs/performance.md

このやり方はSkillsにもそのまま使えます。常時読み込むのはSkill名と用途だけにして、手順本体は必要な時だけ読む方が、多数のSkillを抱えやすくなります。

説明文を増やす前に、検索手段を用意する

「ユーザー関連コードはこの辺にある」と文章で説明するより、AI自身が現在のリポジトリから正確に探せる手段を渡す方が長持ちします。コード検索、型情報、スキーマ、テスト一覧、依存関係グラフ、API仕様を取得できるようにします。

検索方法そのものが複雑なら、tools/repo-queryやbin/ai/findのような薄いラッパーを用意しても構いません。MCPやツール定義も同じで、全ツールのschemaを最初からモデルへ渡すのではなく、必要なツールを検索してから読み込ませる方がコンテキスト消費を抑えられます。

長時間タスクでは、会話の外に「作業メモ」を残す

数時間以上の作業なら、AIに状態ファイルを更新させます。

docs/agent-task.md

Goal: 検索APIを新しいデータストアへ切り替える
Done: read pathの調査、既存test確認、新client実装
Next: timeout時fallbackの実装
Decisions: 旧系へのfallbackは5秒まで
Blocked: productionの実測latencyが未確認
Evidence: benchmark結果は tmp/bench.json

こうしておけば、コンテキスト圧縮やセッション再開が起きても、会話全文から状態を復元する必要がありません。

Googleの11時間ADK最適化でも、長い実行の途中で元の目標を維持する仕組みと、リポジトリ内のSkillを組み合わせています。規約なしの初回実行は公開JSONスキーマを変え、周辺テスト216件しか実行しませんでした。規約を加えた2回目では16,892テストを実行し、レビュー可能なPRまで到達しています。

コンテキスト圧縮では、要約と原文の両方を残す

圧縮後の会話には要点だけを残し、元のログや調査結果は検索できるファイルへ保存します。

会話に残す: 「timeoutはDBではなく外部API待ち。詳細は tmp/investigation-42.md」

ファイルに残す: 実行コマンド、ログ、比較した仮説、除外した原因、raw benchmark。

要約だけにすると、後で判断を疑ったときに検証できません。とくにエラー原因、セキュリティ判断、仕様上の例外は原文へ戻れるようにします。

指示ファイルはコードと同じように変更元を確認する

AGENTS.mdやCLAUDE.mdが変更されたら差分を確認します。外部から取得したSkillやMCP設定も同様です。

- package install は必要時のみ確認する
+ package install は常に自動承認する

- network: docs.example.com のみ
+ network: *

指示ファイルは文章でも、AIにshellやnetwork操作をさせる制御入力です。設定サプライチェーン研究では3,171の公開リポジトリを分析し、16.0%でセキュリティ上の欠陥を確認しています。査読前研究のため数値の一般化には注意が必要ですが、設定を依存物として扱う理由にはなります。
