コンテキスト設計 · 2026-10-26

AIに渡す情報は、量より「いつ必要か」で設計する

最初から全部を読ませません。AGENTS.mdやCLAUDE.mdには毎回必要なルールだけを置き、詳しい手順や背景は別ファイルへ分けます。AIには必要になった時点でそのファイルを読ませます。

推奨信頼度: 中〜高

AGENTS.mdやCLAUDE.mdは「百科事典」ではなく入口にする

やることは単純です。 毎回守るルールだけをAGENTS.mdやCLAUDE.mdへ書き、機能別の細かい説明は別ファイルへ逃がします。

Railsのリポジトリなら、入口はこのくらいで十分です。

bin/setup で初期化。テストは bin/rspec、静的解析は bin/rubocop。

業務ロジックは controller に置かず、既存の service / model 境界に合わせる。認可は Pundit を使い、独自判定を controller に追加しない。DB変更は後方互換を保つ。

公開APIのレスポンス形式を変える必要がある場合は、実装前に停止して影響範囲を報告する。

認可の詳しい実装規約は docs/auth.md、DB変更の規約は docs/database-migrations.md を参照。

たとえば認可を触る仕事なら、AIはまずAGENTS.mdを読み、その後でdocs/auth.mdだけを読みます。DB変更がない仕事で、長いmigration規約を毎回コンテキストへ入れる必要はありません。

この構造にする理由は、AIが一度に扱えるコンテキストが有限だからです。Anthropicは必要な情報を選別することをコンテキスト設計の中心に置いています。GoogleのADK事例でも、リポジトリ規約を.agents/skillsへ分け、短いSKILL.mdから必要な参考文書だけを読む構成を使っています。

詳しい知識は「必要になったら読む」形に分ける

長い設計資料を1つの指示ファイルへ詰め込まず、仕事の種類ごとに分けます。

AGENTS.md
├ 認可を変更する → docs/auth.md
├ DBを変更する → docs/database-migrations.md
├ 公開APIを変更する → docs/api-compatibility.md
├ 非同期処理を変更する → docs/jobs.md
└ 性能調査をする → docs/performance.md

入口側には「いつ、どの文書を読むか」だけを書きます。個別文書には具体例や禁止事項を詳しく書けます。

このやり方はSkillsにもそのまま使えます。常時読み込むのはSkill名と用途だけにして、手順本体は必要な時だけ読む方が、複数のSkillを抱えやすくなります。

リポジトリの説明を増やす前に、検索手段を用意する

「ユーザー関連コードはこの辺にあります」と文章で説明するより、AI自身が正確に探せる手段を渡す方が長持ちします。

Railsなら、次のような調査をAIがすぐ実行できる状態にします。

rg "class .*Users" app/
bin/rails routes | rg users
rg "policy_scope|authorize" app/ spec/
bin/rspec spec/requests/users_spec.rb

必要なら、schema、依存関係、API仕様を返す専用スクリプトも用意する。

大規模リポジトリでは、静的な説明文はすぐ古くなります。検索、型情報、スキーマ、テスト一覧、依存関係グラフの方が現在のコードを直接確認できます。

MCPやツール定義も同じです。全ツールのschemaを最初からモデルへ渡すのではなく、必要なツールを検索してから読み込ませる方がコンテキスト消費を抑えられます。Anthropicも、ツール探索と遅延読み込みをこの用途で提案しています。

長時間タスクでは、会話の外に「作業メモ」を残す

数時間以上の作業なら、AIに次のような状態ファイルを更新させます。

docs/agent-task.md

Goal: 注文検索APIを新DBへ切り替える
Done: read pathの調査、既存test確認、新client実装
Next: timeout時fallbackの実装
Decisions: 旧DBへのfallbackは5秒まで
Blocked: productionの実測latencyが未確認
Evidence: benchmark結果は tmp/bench-20261026.json

こうしておけば、コンテキスト圧縮やセッション再開が起きても、会話全文から状態を復元する必要がありません。

Googleの11時間ADK最適化でも、長い実行の途中で元の目標を維持する仕組みと、リポジトリ内のSkillを組み合わせています。規約なしの初回実行は公開JSONスキーマを変え、周辺テスト216件しか実行しませんでした。規約を加えた2回目では16,892テストを実行し、レビュー可能なPRまで到達しています。ベンダー事例ではありますが、長時間作業ほど「目標」と「リポジトリ知識」を会話の外へ残す価値があります。

コンテキスト圧縮では、要約と原文の両方を残す

圧縮後の会話には要点だけを残し、元のログや調査結果は検索できるファイルへ保存します。

会話に残す: 「timeoutはDBではなく外部API待ち。詳細は tmp/investigation-42.md」

ファイルに残す: 実行コマンド、ログ、比較した仮説、除外した原因、raw benchmark。

要約だけにすると、後で判断を疑ったときに検証できません。とくにエラー原因、セキュリティ判断、仕様上の例外は原文へ戻れるようにします。

指示ファイルはコードと同じように変更元を確認する

AGENTS.mdやCLAUDE.mdが変更されたら、普通のドキュメント変更として流さず差分を確認します。外部から取得したSkillやMCP設定も同様です。

たとえば、次のような変更はレビュー対象です。

- npm install は必要時のみ確認する
+ npm install は常に自動承認する

- network: docs.example.com のみ
+ network: *

指示ファイルは文章でも、AIにshellやnetwork操作をさせる制御入力です。設定サプライチェーン研究では3,171の公開リポジトリを分析し、16.0%でセキュリティ上の欠陥を確認しています。査読前研究のため数値の一般化には注意が必要ですが、設定を依存物として扱う理由にはなります。

根拠

  • Anthropic — Effective context engineering for AI agents。ベンダー一次情報。コンテキスト選別、ツール利用、長時間状態管理の設計指針。
  • Google — 200,000行のADK最適化事例。約20.5万行、約800ファイル、約1.7万テスト。6提案中2件を採用。ベンダー事例。
  • OpenAI — Harness engineering。リポジトリをsystem of recordにし、構造テストやlintでルールを強制した実運用事例。
  • Scanning the Harness。3,171リポジトリの設定を分析した査読前研究。
