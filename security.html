セキュリティ · 2026-10-26

「やるな」と書くより、できないようにする

AIの判断は確率的です。高権限の操作を安全にしたいなら、プロンプトだけで止めず、sandbox、権限、ネットワーク、認証情報の境界を外側で強制します。

推奨信頼度: 高

安全境界はモデルの外に置く

Anthropicは自社製品のcontainment設計について、モデル層だけでは100%防げないため、environment layerでblast radiusを制限すると説明しています。標準的なVM、container、syscall filter、egress controlのような成熟した仕組みを優先し、モデル側の判定は追加層として使います。

これはコーディングエージェントでも同じです。AIが「このコマンドは安全」と判断しても、production credentialsや外部networkが不要なら最初から渡しません。

権限は操作の種類で分ける

機能許可リストは、コマンド名だけではなく「何ができるか」で考えます。たとえばRailsリポジトリなら次のように分けます。

能力通常開発必要時だけ
repo内の読み取り許可-
repo内の編集許可-
repo外filesystem禁止明示承認
インターネット公式docs等へ限定任意hostは明示承認
development DB読み書き可-
production DB禁止別workflow
deploy禁止CI/CD経由

自動承認は便利だが、境界を弱くする

HarnessSecurity-Benchは6種類のcoding harness、23 task、2,500 trialで9種類のsecurity mechanismを比較しています。制御したモデル条件では、auto-approveを有効にしたときattack successが29.2%から95.6%へ上昇しました。network isolationやread-onlyは攻撃を抑える一方で正当タスクも阻害し、command allowlist / denylistは比較的小さいutility lossで効果を示しました。

この研究は査読前で、モデルもGLM-5.2に固定されています。数値をそのまま全製品へ一般化はできません。それでも「承認を消すほど安全になるわけではない」「単純な禁止コマンドだけでなく別経路を考える」という設計上の教訓は強いです。

セキュリティ条件を仕様に書く

Last Secure Code Benchmarkでは150の実脆弱性から450 taskを作り、promptにはsecurity requirementを書かず機能要求だけを与えています。6つのfrontier agentは73.6〜91.3%のtaskを機能的には通しましたが、機能とsecurityの両方を満たした割合は最高でも25.1%でした。

「安全なコードは暗黙に書いてくれる」と期待しない方がよいです。Railsなら、認可はPundit経由、外部URL fetchはSSRF対策済みclientだけ、secretをlogに出さない、SQL文字列連結禁止、といった条件をIssueに書きます。

指示ファイルやSkillも依存物として扱う

AGENTS.md、CLAUDE.md、Skill、hook、MCP設定はAIの動作を変えます。実行コードでなくても、結果としてshellやnetworkを使わせられるため、出所を確認します。

設定サプライチェーン研究では3,171の公開リポジトリを分析し、16.0%でsecurity defectを確認しています。MCP version未固定、広すぎるshell grant、Skillがshellを事前承認する例などです。公開marketplaceの便利な設定をそのまま本番権限へつなげない方がよい理由になります。

承認ルールそのものも攻撃対象になる

2026年10月の研究では、リポジトリ内の悪意ある文脈がagentに「もっともらしいが広すぎるallow rule」を要求させ、ユーザーが承認すると以後の保護を弱められる問題をClaude CodeとCodex CLIで検証しています。58%の実験で狙ったallow ruleを要求させ、承認後に条件を満たしたケースの81%でsilent goal completionに成功したと報告しています。

「この種類のコマンドは今後すべて許可」のような永続許可は、その場の作業だけで判断しません。scope、期限、対象directoryを狭くします。

実務では、開発環境と本番操作を分ける

日常のcoding agentはdevelopment workspaceだけに閉じ込め、本番変更はCI/CDや専用operation workflowに渡す方が安全です。たとえばmigration fileはAIが作れても、production migrationの実行権限までは渡さない、という分離です。

監査ログには、誰のagentが、どの認証情報で、どのtoolを呼び、何を変更したかを残します。後から「モデルが何を考えたか」より「システム上何をしたか」を追えることの方が重要です。
