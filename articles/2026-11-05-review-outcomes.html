AIレビューの価値は「何件指摘したか」では測れない

レビューAIの出力件数を増やしても、開発者が直さない指摘ばかりなら負担が増えます。採用された指摘と、その後に人間が見つけた問題を分けて追うと、レビュー品質の改善に使える指標になります。

指摘数だけでなく、採用された割合を測る

GitHubは2026年11月5日、Copilot usage metrics APIのリポジトリ日次レポートにcopilot_code_reviewを追加しました。total_comments_evaluatedとtotal_comments_addressedから、レビュー指摘への対応率（addressed rate）を算出できます。指摘のseverity、review tier、bug/security/custom分類、custom instructions・skills・MCPによるカスタマイズの有無も集計できます。

addressed_rate = total_comments_addressed / total_comments_evaluated

分母が0なら割合は未定義です。指摘はPRのマージ時点で評価されるため、コメント投稿日の集計ではありません。また「対応済み」にはコード修正だけでなく、後続PRで直すという返信も含まれます。したがってaddressed rateは「バグ修正率」でも「正しい指摘の割合」でもありません。

小さな集計例

次のPythonは、APIの実データではなく仮の数値を使って、ゼロ除算と指摘件数の罠を確認する実験です。Python 3のみで動きます。

cases = {
    "A": {"evaluated": 100, "addressed": 30},
    "B": {"evaluated": 40, "addressed": 24},
    "C": {"evaluated": 0, "addressed": 0},
}
for name, row in cases.items():
    n = row["evaluated"]
    rate = row["addressed"] / n if n else None
    print(name, "N/A" if rate is None else f"{rate:.1%}")

期待出力はAが30.0%、Bが60.0%、CがN/Aです。Bは指摘件数が少なくても対応率が高い一方、どちらが重大な不具合を多く防いだかは、この数値だけでは分かりません。

本番運用では三つを並べる

まず、指摘への対応率をseverityやカテゴリ別に追います。次に、人間の追加change request、マージ後のrevert・hotfix・回帰bugを追います。最後に、レビューに費やした人間の時間とAIの利用費を比較します。リポジトリや変更難度の違いを無視した横断ランキングは避けます。

APIにはtotal_merged_no_human_change_request_after_reviewもありますが、これは「Copilotレビュー後に人間から変更要求がなかったマージPR数」です。人間が十分に確認した証拠でも、欠陥がなかった証拠でもありません。

GitHubの公開したReviewBenchの社内オンラインA/B試験では、addressed rateが相対8.0%増、recallが13.6%増、コメント数が61%増でした。ただしベンダー自身の評価であり、別組織のコードベースでも同じ改善が得られるとは限りません。

導入条件と限界

このレポートはEnterprise/Organizationのrepos-1-dayで提供され、閲覧には権限とCopilot usage metrics policyの有効化が必要です。Botが作成したPRでは通常コメント評価が行われない点にも注意してください。独自エージェントで同じ指標を使う場合は、コメントの追跡、修正との対応付け、人間のレビュー、マージ後の不具合を別々に記録します。
