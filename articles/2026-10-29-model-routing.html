モデル選択を毎回人間がやらない。ルーティングとカスケードが実用機能になった

「軽い仕事は安いモデル、難しい仕事は強いモデル」という設計が、手動の使い分けから実行基盤側の仕事へ移りつつあります。GitHub Copilot Fusionは、単一モデル、段階的なエスカレーション、別モデルによる批評をタスクごとに切り替える仕組みを一般提供しました。

3つの実行パターン

方式動き向く仕事
Single1モデルでそのまま完了する定型的で失敗コストが低い作業
Cascade軽量モデルで試し、品質判定で不足なら強いモデルへ上げる大半は簡単だが一部だけ難しい作業
Critique1モデルが作り、別モデルが読み取り専用で批評し、元モデルが修正する設計やレビューなど見落としを減らしたい作業

重要なのは「最強モデルを固定する」以外の選択肢が製品機能として定着したことです。ルーターはタスクの難しさとコストを見て実行経路を変えます。

自前で使うなら、まずCascadeから始める

独自Agentでも同じ考え方を使えます。安いモデルで実行し、決定論的テストやgraderで合格しなければ強いモデルへ上げます。モデル自身の「自信がある」という申告だけを判定基準にせず、テスト、schema validation、lint、既知fixtureなど外部の証拠を優先します。

result = fast_model(task)
if deterministic_checks(result):
    return result
return strong_model(task, previous_attempt=result)

Critiqueは追加tokenと待ち時間が発生するため、全タスクへ機械的に入れるより、変更範囲が広い、仕様が曖昧、安全性が重要、といった条件で使います。

ベンダー測定は自社タスクへそのまま移さない

GitHubはArtificial Analysis Coding Agent IndexでFusion Maxが60点、Claude Code + Opus 5.5 Maxとの差が2点以内で、平均APIコスト・tokenは約半分、所要時間は約40%短かったと報告しています。ただしこれはGitHubが示した特定benchmarkの結果で、一般的な開発費用を半減できる証拠ではありません。

導入時は20〜50件程度の自社golden setで、成功率、総token、再試行、人間review時間、完了時間を比較します。

ローカルモデルもルーティング対象になった

Copilot Fusionでは実験的に、対応するローカルモデルとcloud modelの間も自動ルーティングできます。ただしrouting判定自体はcloudで行われるため、「ローカル推論を選べばセッション全体がofflineになる」という意味ではありません。機密性の要件では、推論場所だけでなくrouterへ何が送られるかも確認が必要です。

根拠と限界
