AIに安全判定を任せる権限モードは「全許可」と「毎回承認」の中間になる

GitHub CopilotのAssisted permissionsが2026年10月26日に一般提供されました。コマンド、filesystem path、URLへのアクセス要求をLLMが評価し、「明らかに安全」と分類したものだけ自動で通し、それ以外は人間へ承認を求めます。承認疲れを減らす実用的な仕組みですが、sandboxやcredential分離の代わりにはなりません。

何が変わったか

Copilot CLI、Copilot app、Visual Studio CodeでAssisted permissionsを選べるようになりました。従来の「毎回人間が承認する」と「広く自動承認する」の間に、要求ごとにモデルが安全性を分類する運用が入ります。EnterpriseではAllow Allを禁止しつつAssistedだけ許可する、Assisted自体を禁止する、初期permission modeを指定するといった管理もできます。

実務では、テスト実行やrepo内の通常操作のような低リスク要求で承認回数を減らしながら、判断が曖昧な操作を人間へ戻す使い方が考えられます。

ただし、LLMの安全判定はハードな境界ではない

ここで重要なのは、Assistedが「モデルの外側にある権限制御」を置き換える機能ではないことです。LLMによる分類は誤る可能性があります。production credentialを渡さない、repo外filesystemを閉じる、network destinationを制限する、deployをCI/CDへ分離するといった境界は引き続き必要です。

安全設計は、まずOS・sandbox・credential・network・tool policyで「そもそもできない範囲」を作り、その内側でAssistedのようなモデル判定を使って承認負荷を下げる順序が扱いやすいです。

自動承認よりは細かいが、手動承認より安全とはまだ言えない

GitHubの発表は製品仕様の一次情報であり、Assisted permissionsの事故率や誤分類率を独立比較した研究ではありません。したがって「手動承認と同等に安全」「Allow Allより何%安全」といった効果量は現時点では言えません。

既存のHarnessSecurity-Benchでは、別条件の実験ながらauto-approveが攻撃成功率を大きく上げた結果が出ています。これはAssistedそのものの評価ではありませんが、承認を完全に消す設計を避ける根拠にはなります。

使うなら、失敗しても被害が小さい環境で

開発用workspaceではAssistedを使い、本番操作やsecret変更、任意hostへのnetwork accessは別workflowへ分ける構成が無難です。企業では「Allow Allは禁止、AssistedまたはManualのみ」のようにpolicyで上限を固定すると、個人設定で安全境界が消えるのを防げます。

監査時には、モデルが安全と判定した理由だけでなく、実際にどのcommand・path・URLが自動許可されたかを追えるログを残します。モデル判定は補助層、実行ログは事実の記録として扱います。

根拠と限界

  • GitHub — Copilot assisted permissions generally available（2026-10-26）。対象クライアント、LLMによる要求分類、Enterprise policyを確認できる製品一次情報。
  • セキュリティガイド。sandbox、権限分離、自動承認、permission rule escalationに関する研究をまとめています。

Assisted permissions自体について、独立した攻撃耐性評価や誤分類率の公開データは今回確認できませんでした。製品の一般提供と、安全性の実証は分けて扱う必要があります。
