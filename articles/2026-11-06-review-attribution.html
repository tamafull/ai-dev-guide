AIレビューの指摘は「何を参照して出したか」まで追える

AIのレビュー指摘を採用する前に、レビューの実行条件と参照情報を残す。GitHub Copilot code reviewは2026年11月6日、APIでレビューとコメントの明示的な帰属、レビューのeffort、指摘に使われたSkills・MCP・カスタム指示の情報を取得できるようになった。指摘の正しさ自体は別途検証が必要だが、再現性と監査の材料が増えた。

レビューの評価単位を「コメント」から「実行条件付きの指摘」に変える

同じPRでも、レビューのeffort、カスタム指示、MCPの接続先が異なれば、指摘の内容とコストは変わり得る。評価時にはPR番号とコミットSHAに加え、レビュー日時、effort、指摘の分類、使用したSkills/MCP/指示、AI credits、指摘の採否とその理由を残す。情報がAPIに存在しない場合は「不明」として扱い、推測で埋めない。

記録するもの使い道
PR・commit SHA・review IDどの差分を判定したか固定する
effort・モデル構成・AI credits品質と費用の比較条件を揃える
Skills・MCP・custom instructions指摘の参照条件を追跡する
採用・却下・修正後のテストレビュー結果と欠陥修正を分けて評価する

APIが示すのはCopilotが「参照元として報告した」情報であり、実際の内部推論の完全な証跡ではない。指摘の根拠として表示されたファイルやコード行を独立に確認する。

運用例：レビュー設定をリポジトリ単位で固定する

  1. GitHubのレビュー設定で対象リポジトリのeffortとカスタム指示・MCPの利用方針を決める。
  2. レビュー後にAPIからreview ID、effort、帰属、利用したカスタマイズの情報を取得してログへ保存する。
  3. 同じ種類のPRを同じ条件で比較し、誤検知、重大な見逃し、修正率、レビュー時間、AI creditsを集計する。
  4. 設定変更時は旧設定と新設定を別群として扱い、既存の回帰用PRを再評価する。

GitHubの設定APIはenterprise・organization・repositoryの階層に分かれる。上位階層で管理された設定は下位から上書きできない。Enterprise/Organizationの設定エンドポイントではGitHub Appsとfine-grained PATが使えない一方、repository設定は対応する権限付きの認証で扱える。認証方法と利用可能なeffortは公式設定APIガイドで確認する。ここでは仕様未確認のURLやリクエスト例を実行可能コードとして示さない。

複数モデルでレビューしても「正しい」とは限らない

同じ発表ではBalanced effortのレビューが3つのreviewer modelと結果統合用のモデルを使うようになったと説明されている。これは複数の観点を集約する製品実装の変更であり、単一モデルよりどの程度欠陥検出率が改善したかを示す独立実験ではない。複数モデルの一致も、共通の誤解や同じ不足情報による誤判定を排除しない。

実務では、重大な指摘は再現テストや関連コードの調査で裏付ける。見逃しの評価には人間が確認した欠陥入りPRやholdoutを使い、指摘数や対応率だけで品質を判断しない。

今回の変更と限界

GitHubはレビューのAPI管理、明示的な帰属、利用したカスタマイズ情報、AI creditsの表示を2026年11月6日に公表した。取得可能なフィールドは設定やメタデータの有無によって異なる。発表は機能提供の一次情報であり、レビュー品質や生産性の改善効果を独立に証明したものではない。
