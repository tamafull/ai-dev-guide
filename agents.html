エージェント構成 · 2026-10-26

最初から多人数にしない。独立できる仕事だけ分業する

複数エージェントは強力ですが、役割を増やすだけで品質が上がるわけではありません。基本は主エージェント1つ。調査、レビュー、比較のように互いに独立しやすい作業だけ補助エージェントへ分けます。

条件付き推奨信頼度: 中

分業の判断基準は「同時に進めても衝突しないか」

並列化しやすいのは、同じファイルを触らず、互いの途中結果を待たなくても進められる仕事です。たとえばリポジトリ調査、セキュリティレビュー、性能ボトルネックの候補探索、複数案の比較です。

逆に、設計→実装→検証を理由なく別エージェントへ渡すだけでは、引き継ぎで情報が落ちます。同じファイルを複数エージェントが同時に編集すると、競合解消まで含めて仕事が増えることもあります。

大きな機能改修なら、探索だけを並列化する

たとえば請求機能を大きく改修するとします。主エージェントがIssue全体を持ち、次のような調査だけを並列化します。

  • 補助エージェントA: 課金関連のdomain/service/jobの依存関係を調べる。
  • 補助エージェントB: 既存の失敗時リトライ、二重請求防止、idempotency keyの実装を調べる。
  • 補助エージェントC: 既存テストと監視・アラートを調べ、検証項目を提案する。

実装方針の統合と最終差分は主エージェントが持ちます。この形なら、並列化で探索時間を短くしつつ、設計判断の責任点は1つに保てます。

補助エージェントの要約だけを監査記録にしない

主エージェントが受け取るのは多くの場合、補助エージェントが作った要約です。要約は便利ですが、実際に実行したコマンド、失敗した操作、読み込んだ外部データまでは残らないことがあります。

高権限の作業では、各エージェントのツール呼び出しを外部の実行履歴へ残します。親子関係、操作対象、実行結果、承認の有無が後から追える形が望ましいです。

長時間作業は「役割数」より状態管理が先

Anthropicの長時間アプリ開発事例では、planner / generator / evaluatorの3役を使っていますが、効いているのは役割名そのものではありません。作業を小さなsprintへ分け、仕様と成果物を残し、評価役が実際のアプリを操作して不具合を返すループが中心です。

同じ記事では、単一エージェント20分・約9ドルに対し、フルハーネスは6時間・約200ドルでした。品質差は大きかった一方、20倍超のコストがかかっています。多段構成は、失敗コストが大きい長時間タスクに絞るべきです。

並列エージェントは、大きな探索空間では有効になり得る

Anthropicは16エージェントを使ってCコンパイラを構築する実験を公開しています。約2,000 Claude Code session、API費用約2万ドルで、Linux kernelを複数アーキテクチャ向けにコンパイルできる約10万行のコンパイラを作りました。

これは印象的な事例ですが、一般的な業務開発の費用対効果を証明するものではありません。大きな探索空間、豊富な自動テスト、並列化可能な問題という条件が揃った特殊な実験です。普通のWeb開発で16体を動かす根拠にはなりません。

分業するなら、最初に共有状態を決める

複数エージェントを使う場合、最低限次を共有します。

  • 全体の目的と受け入れ条件。
  • 誰がどの領域を担当しているか。
  • 編集禁止ファイルやファイル所有権。
  • 完了済み・未完了・ブロック中の状態。
  • 判断理由と検証結果。

一時的なメッセージだけで協調させるより、リポジトリ内の計画ファイル、Issue、タスクDBなどを共有状態にした方が再開しやすくなります。

根拠

  • Anthropic — Harness design for long-running application development。planner/generator/evaluator構成の実験。単一runとの比較はあるが、一般化されたbenchmarkではない。
  • Anthropic — Building a C compiler with a team of parallel Claudes。16エージェント、約2,000 sessionの大規模実験。特殊な条件のベンダー事例。
  • OpenAI — Harness engineering。人間が意図と環境を設計し、Agentが実行する運用事例。
