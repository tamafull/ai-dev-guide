AI Development Guide / Living Standard

現在のAI開発をどう設計するか

人間が目的・制約・正解条件を設計し、AIエージェントが探索・実装・検証を回す。Agentの自己申告ではなく、独立したテスト・ポリシー・レビュー・監査で完了を判定する。

推奨信頼度: 中〜高最終更新: 2026-10-26

中核原則: 「どのモデルが最強か」より、仕様・検証・権限・監査・コストを含む Harness 全体を評価する。

1. 仕様を先に固定

Acceptance Criteria、Security Criteria、Stop Criteriaを先に定義する。

2. 外部検証でDoneを決める

Agentが作ったコードをAgentが書いたテストだけで自己採点しない。

3. 権限はallowlist

filesystem / network / credentials / MCPを能力単位で開き、境界違反時はfail closed。

4. 成果をend-to-endで測る

LOCやPR数ではなく、Lead Time・review・rework・defect・総コストを追う。

Workflow

推奨 Agentへ実装を依頼する前に正解条件と禁止境界を定義し、大きな変更ではExploreとPlanを分離する。

Issue / Goal — なぜ必要か、何を変えないか
↓
Specification — Acceptance / Security / Stop Criteria
↓
Explore — 関連コード、既存テスト、API契約、依存関係
↓
Plan — 変更点、migration、validation、rollback
↓
Implement — 小さなslice、既存の決定論的toolを優先
↓
Validate — test / type / lint / security / repo policy / holdout
↓
Review — AI一次review + risk-based human review
↓
Merge / Operations — post-merge fix・revert・regressionまで追跡

Specification

Acceptance Criteria

「この変更を完成と判定してよい条件」。機能要求をAgentが検証可能な形へ落とす。

Security Criteria

「安全に実装する」のような曖昧指示ではなく、認証・認可・入力検証・secret・外部通信などを具体化する。

Stop Criteria

Agentが自力で続行せず人間へ返す条件。例: production credentialが必要、許可外networkが必要、同一failureを繰り返した、予算上限超過。

Context Engineering

推奨 大量の文書を常時入れるのではなく、必要な情報を必要な時に見せる。

  • AGENTS.md / CLAUDE.md: build/test command、repo map、invariant、decision rule、stop conditionに絞る。
  • Progressive disclosure: 詳細はSkillsやreferenceへ分離し、必要時に読む。
  • Compaction: 反復的tool outputを機械的に削り、必要ならsummaryする。
  • Instruction trust: AGENTS.md等もAgentのcontrol inputなのでsecurity-sensitive configurationとして扱う。

Agent Architecture

条件付き推奨 Defaultはsingle main agent。独立性がある仕事だけsubagent化する。

向く向かない
repo探索、security review、performance調査、独立案比較Plan→Implement→Verifyを機械的に別Agentへリレー、同一ファイル同時編集

親Agentのsummaryだけを信用せず、subagentのtool/action履歴は外部audit logへ残す。

Tools & MCP

推奨 決定論的に解ける部分をLLMへ再推論させない。

問題優先
既知commandで検証可能CLI / script / checker
外部systemへの構造化操作MCP / typed tool
曖昧な設計判断LLM reasoning

MCP

Model Context Protocol。能力を増やす仕組みであり、Agentの判断力そのものではない。接続数よりtool discovery・decision rule・最小権限を重視する。

Testing & Review

推奨 Agentの自己採点だけで通さない。

Independent Test Oracle

「正解」を実装Agentから独立して定義する。重要なAcceptance Criteriaは既存contract test、holdout test、別評価系、人間定義などで独立性を確保する。

Holdout Test

実装Agentが直接最適化できない検証用テスト。benchmarkでの過適合や「reference implementationの挙動を正解と誤認する」問題を減らす。

Risk-based Human Review

変更人間レビュー
docs / small refactor / deterministic migration軽め
business rule / auth / billing / schema / distributed state深いレビュー
高権限infra / production mutation必須 + rollout/rollback確認

Security

推奨 Prompt policyをsecurity boundaryにしない。

  • Agent sandboxが壊れる前提でVM/container等の外側境界も用意する。
  • Capability Allowlist: filesystem / network / credentials / MCP / CIを能力単位で必要な分だけ開く。
  • auto-approveを常用しない。
  • 未知repo・Downloads・home directoryからAgentを起動しない。
  • AGENTS.md / CLAUDE.md / Skills / MCP / Pluginsのprovenanceを確認する。
  • Plugin/Skill/Extensionはversion/hashを固定し、可能ならsignature/provenanceを検証する。
  • policy violation時はtool freeze → human review。

CI/CD & Operations

推奨 Agentを普通のproduction systemと同様に観測する。

Observability

task → model call → tool call → CI → PRまでtraceし、retry・failure・cost・human interventionを追跡する。

Durable Execution

長時間taskはdurable stateへgoal/plan/progressを保存し、再開時の副作用二重実行を避ける。DB migrationや外部変更ではidempotency / operation IDを意識する。

Cost & Token Efficiency

推奨 最小tokenではなく success-per-total-usage を最適化する。

総コストにはinput/output token、cache、retry、tool再実行、wall-clock、validation、人間review、post-merge reworkを含める。cheap explorer → strong implementerのroutingは候補だが、task別benchmarkで決める。

Metrics

LOC・commit・PR数だけでは生産性を評価しない。

領域推奨KPI
DeliveryIssue完了、Lead Time、deployment frequency
QualityCI retry、review change request、post-merge fix、revert、production defect
Humanreviewer時間、intervention回数、architecture review負荷
Agentsuccess rate、tool calls、retries、wall-clock、token、cost

Glossary

Harness

モデルの周囲にある実行ループ、context管理、tools、permissions、retry、validation等の仕組み。

Context Engineering

Agentへ何を、いつ、どの形で見せるかを設計すること。

Trajectory

Agentのmodel call / tool call / action / resultの一連の履歴。

Compaction

長いcontextを圧縮して長時間taskを継続可能にする仕組み。

Tool Search

全tool schemaを常時contextへ入れず、必要なtoolだけ発見・ロードする方式。

Behavioral Contract

API表面だけでなく、nil、timezone、transaction、callback、error、side effect等を含む既存挙動の契約。

Evidence

このガイドでは、一次情報・独立研究・査読前論文・コミュニティを区別し、ベンダーbenchmarkを独立証拠として扱わない。

Candidates

General-purpose多数Agent構成保留coordination/token overheadに対し安定改善の証拠不足。複数実務benchmarkで再現すれば再検討。
