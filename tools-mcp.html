ツールとMCP · 2026-10-26

決まった処理はツールに任せ、AIには判断が必要な部分を残す

AIに全部を考えさせるより、再現可能な処理はCLI、スクリプト、lint、APIへ寄せた方が速く、安く、監査しやすくなります。MCPは外部能力をつなぐ手段であり、判断そのものを改善する仕組みではありません。

推奨信頼度: 中〜高

まず「AIが考える必要があるか」を疑う

テスト実行、schema確認、依存関係の列挙、静的解析、ログ集計のような仕事は、同じ入力なら同じ結果が出るツールへ任せます。AIが毎回コマンド列を推論する必要はありません。

仕事向いている手段
RSpecを対象別に実行する固定CLI / wrapper script
APIやSaaSを操作するMCP / typed API tool
10,000行の結果を絞り込むコード実行環境でfilterして要約のみ返す
設計案を比較するLLM reasoning

Railsでは「調査用コマンド」を揃えるだけでも効く

たとえば次のようなスクリプトを用意しておくと、AIが毎回grep方法やSQLを考える必要がなくなります。

bin/ai/test path/to/spec.rb — 必要な前処理込みで対象テストを実行
bin/ai/routes users — 関連routeだけ表示
bin/ai/schema users — table定義とindexを表示
bin/ai/deps Billing::Charge — 依存関係を機械的に列挙
bin/ai/check — lint / type / unit test / policy checkをまとめて実行

この種の「狭いが確実な道具」は、プロンプトを長くするより長期的に効きます。

MCPは、既存の認証・監査を再利用できる形がよい

Google Cloudは既存のOpenAPI定義からAPI GatewayをMCP serverとして公開する機能を提供しています。新しいMCP serverを別に実装せず、既存APIの認証、quota、loggingをそのまま使う方向です。

社内APIをAIへ触らせる場合も同じ考え方が使えます。AI専用の抜け道を作るより、既存のAPI gatewayや権限制御を通し、その上で読み取り専用・書き込み可能を分けます。

ツール定義を全部コンテキストへ入れない

ツールが増えると、schemaやdescriptionだけでコンテキストを消費します。Anthropicは、必要なツールを検索してから読み込むprogressive disclosureを提案しています。大量データもモデルへ直接返さず、実行環境でfilter・join・aggregateして必要な部分だけ返す方が効率的です。

例えばGoogle Driveから10,000行を取得してAIに絞り込みをさせるより、コード実行環境で「status=pending」だけを抽出し、件数と数件の例だけをモデルへ返します。

ツールを増やすほど、権限設計も細かくする

MCPを追加するとできることが増えます。同時に、prompt injectionから到達できる操作も増えます。読み取り、作成、更新、削除を同じtool setにまとめず、業務に必要な能力だけ公開します。

特にproduction DB、CI/CD、クラウド管理、メール送信、課金APIのような副作用の大きいtoolは、別credentials・別workspace・明示的なapproval boundaryを用意した方が安全です。

「ツール化する価値」は利用回数と失敗コストで決める

一度しか使わない処理までMCP化する必要はありません。繰り返し使う、引数schemaが明確、失敗時の影響が大きい、結果を監査したい、といった条件が揃うほどツール化の価値が上がります。

逆に、探索的な調査を無理にツールへ固定すると柔軟性を失います。最初はCLIやスクリプトで試し、安定した手順だけ高水準toolへ昇格させる方が扱いやすいです。

根拠

  • Anthropic — Code execution with MCP。tool definitionの遅延読み込み、大規模データの事前処理、状態保存を説明。ベンダー一次情報。
  • Google Cloud — REST APIをMCP toolとして公開。既存認証・quota・loggingを再利用する実装例。
  • OpenAI — Codex as a platform。harnessがtool、approval、context gatheringを仲介する構成を説明。
